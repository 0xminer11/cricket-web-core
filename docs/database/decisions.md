# Decisions and deviations

Where the Module 2 brief and Module 0/1 disagreed, Module 0/1 won and the difference is recorded here instead of being silently redesigned.

## Module 0 wins over the brief's examples

| Brief example                                                     | What is persisted                                                                                                                                                                                                                                                                                                                                             |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Batting `reaction`, physical `speed`                              | Not in Module 0. Batting: timing, power, placement, defence, footwork, shotSelection, technique, consistency. Bowling: pace, accuracy, swing, seam, spin, control, variation, consistency. Physical: strength, stamina, fitness, reflex, agility, recovery. Columns are prefixed `batting_`/`bowling_`/`physical_` because `consistency` exists in two groups |
| Personality `aggression`, `team_chemistry`                        | Module 0 has confidence, discipline, leadership, professionalism, riskAppetite, teamMindset                                                                                                                                                                                                                                                                   |
| Career tier "Local"                                               | Module 0 tiers are academy, club, district, domestic, franchise, international. The lowest (`academy`) is the "Local" tier used by the development player                                                                                                                                                                                                     |
| Wallet types `MATCH_REWARD` (upper case)                          | Stored lower snake_case (`match_reward`) like every other enum-like value. Adds `starter_grant`, `item_sale`, `career_event_reward`, `contract_payment`, `sponsor_payout` for Module 0 flows                                                                                                                                                                  |
| Acquisition sources `match_reward`, `career_reward`, `shop_coins` | Module 0 sources (`starter, shop, reward, achievement, contract, sponsor`) plus `premium_purchase, admin_grant, promotion`                                                                                                                                                                                                                                    |
| Match statuses without a Module 0 counterpart                     | Module 0 `MatchState.status` is a subset of the persisted set (`created, ready, in_progress, completed, abandoned, cancelled`)                                                                                                                                                                                                                                |
| Appearance definitions                                            | Module 0 defines none. `player_appearance` stores opaque `namespace.name` ids (shape-checked); the character-creator module owns the catalogue and validation                                                                                                                                                                                                 |
| Competition definitions                                           | None in Module 0. `fixtures.competition_definition_id` is an opaque `competition.*` id until a definition module exists                                                                                                                                                                                                                                       |
| Contract "type" and `performance_bonus_config`                    | Module 0 contracts are typed (salary, match fee, bonus coins, minimum rating, duration in matches). Those are columns; extra terms go in `terms_snapshot` JSONB                                                                                                                                                                                               |

## Structure choices

- **No `player_profiles.career_id`.** `careers.player_id` is the link; a two-way pair would create a circular insert. A partial unique index allows one _active_ career per player while retired careers accumulate, which also leaves room for multiple profiles later (drop `player_profiles_user_id_uniq`).
- **Career-bound counters live on `careers`** (`current_tier`, `reputation`, `selector_interest`, `fans`); `player_state` holds level, XP, form, fatigue. The brief listed reputation/selector interest/fans in both places; one home avoids two sources of truth. Career matches/wins come from `player_stats`, not from duplicated counters.
- **Form history is derived**, not stored: `match_participants.performance_rating` (0-10) already records every match, and `getRecentPerformanceRatings()` returns Module 0's `recentPerformanceRatings`. Only the current `form` value and `form_updated_at` are persisted.
- **Skill progression is sparse rows** in `player_skill_progress(player_id, stat_key, skill_xp)`, key restricted to the 22 trainable stats. `xpToNextPoint` is derived from the stat via Module 0's `skillXpToNextPoint`, so it is never stored. Sparse rows keep atomic `INSERT .. ON CONFLICT DO UPDATE SET skill_xp = skill_xp + n` trivial; 22 extra columns would not.
- **Stats use one table with scope columns** `(player_id, scope_type, scope_id)`: `career/all`, `season/<n>`, `format/format.5_over`, `competition/<id>`. Only base counters are stored; averages, strike rate, economy are pure functions in `stats-derivations.ts`.
- **Balls reference participants, not player profiles.** `match_balls.striker_participant_id` etc. point at `match_participants`, so AI players (no profile) and PvP are handled identically, and composite foreign keys prove they belong to the same match.
- **`match_balls.id` is a `bigint` identity**, not a UUID: it is the highest-volume table, never exposed by an API, and narrow keys keep indexes small. Ordering uses `sequence_number` (per innings), not the id or a timestamp.
- **`training_sessions` is indexed by `started_at`**, not `completed_at`: list pages sort by start and `completed_at` is NULL for in-flight sessions.
- **Equipment upgrade history is not a separate table.** An upgrade is `player_inventory.upgrade_level` (compare-and-set) + a `wallet_transactions` row (`item_upgrade`, referencing the inventory item) in one transaction. That already answers "who paid what, when, for which item"; add `item_upgrade_transactions` only if failed-upgrade or refund flows appear.
- **Seasons are not a table.** `careers.season_number` and `fixtures.season_number` are enough; a `seasons` table belongs to the LiveOps module.
- **`DATA_SCHEMA_VERSION` is now 2.** Version 1 was Module 0's in-memory `PlayerSave` contract; version 2 is the first relational persistence structure. Increment it (and add a migration) whenever persisted structure changes significantly. Matches pin it in `matches.data_schema_version`.
- **`game_versions` is informational.** Source constants remain authoritative; `seedReferenceData()` records the version triple compiled into each release.
- **`database` may depend on `game-core` and `logger`** (dependency rules updated). `game-core` has no dependencies, so no cycle; `schema/` itself never imports it, so drizzle-kit needs no build.

## Not built (by design)

Authentication tables, character-creator flows, cricket/XP/reward formulas, leaderboards, payments, LiveOps, admin mutations, `match_events`, partitioning.
