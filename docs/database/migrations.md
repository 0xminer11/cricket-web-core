# Migrations

All schema changes are migrations. `db push` and ad-hoc DDL are not used anywhere; production changes only via `pnpm db:migrate`.

## Files

| Migration                 | Content                                                                                                                                   |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `0000_initial_schema`     | Generated by drizzle-kit: all 30 tables, foreign keys, CHECK/unique constraints, indexes                                                  |
| `0001_integrity_triggers` | Hand-written (`drizzle-kit generate --custom`): `touch_updated_at`, append-only guards, ledger-only balance writes, monotonic lifetime XP |

Naming: sequential number + snake_case description (`NNNN_verb_noun`). Commit the SQL together with `meta/_journal.json` and the snapshot.

## Workflow

1. Edit `packages/database/src/schema/*` (and `enums.ts`/`limits.ts` when a list or range changes).
2. `pnpm db:generate` (or `pnpm db:migrate:dev`). Trigger/function changes: `pnpm --filter @the-cricketer/database exec drizzle-kit generate --custom --name=<name>` and write the SQL by hand, separating statements with `--> statement-breakpoint`.
3. **Review the SQL** in the pull request: locks, table rewrites, backfills, index builds.
4. Run `pnpm db:migrate` locally, then `pnpm db:test` (includes the fresh-database and step-by-step upgrade tests).
5. CI repeats: migrate an empty database, seed twice, `pnpm db:drift` (regenerate and fail on any difference), integration tests.
6. Deploy to staging, verify, then production. Applying is serialised by a session advisory lock, so several replicas starting at once are safe.

Constraint names are explicit and at most 63 characters (a longer auto-generated name would be truncated by PostgreSQL and cause perpetual drift).

## Safe-change rules

- **Additive first.** Add nullable column or table -> deploy code that writes it -> backfill in batches -> add `NOT NULL`/constraint in a later migration. Never add a `NOT NULL` column without default to a populated table in one step.
- **Expand/contract for renames and type changes**: add new, dual-write/read, backfill, switch, then drop in a later release. Destructive drops only after no deployed release reads them.
- **Indexes on large tables** (`match_balls`, `wallet_transactions`): use `CREATE INDEX CONCURRENTLY` in a hand-written migration (it cannot run inside a transaction: put it in its own migration file with a comment). Adding CHECK constraints to populated tables: `ADD CONSTRAINT ... NOT VALID` then `VALIDATE CONSTRAINT`.
- **Changing an enum-like list**: drop/add the CHECK in one migration; also update `enums.ts`.
- **Changing a mirrored limit** (`limits.ts`, e.g. level cap) needs a migration plus the Module 0 change; `tests/db-unit.test.ts` fails if they diverge.
- Bump `DATA_SCHEMA_VERSION` for significant structural changes and record the change in `docs/architecture/versioning.md`.
- Migrations are **forward-only**. Recovery is a corrective forward migration or restoring a verified backup with a compatible release, never an automatic down-migration. Back up before every production migration.

## Development reset

`pnpm db:reset` drops the `public` and `drizzle` schemas and reapplies migrations. It refuses to run unless `APP_ENV`/`NODE_ENV` is development or test **and** `DATABASE_URL` points at `localhost`, `127.0.0.1`, `::1` or the `postgres` service. It is not referenced by CI deploy steps, images or entrypoints and must never be added to them.

## Tested guarantees

`tests/db/migrations.test.ts`: (1) a completely empty PostgreSQL is migrated to the latest schema and seeded; (2) an existing database at `0000` (with data) is upgraded by the later migrations and re-running is a no-op; (3) the expected tables, constraints, indexes and triggers exist; (4) no `timestamp without time zone` columns exist and every `id` is `uuid` except `match_balls`.
