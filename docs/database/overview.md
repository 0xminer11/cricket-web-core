# Database overview

Module 2 adds the persistent PostgreSQL layer. PostgreSQL is authoritative for everything a player can gain or lose: currencies, XP, level, skills, inventory, equipment, contracts, career progress, match results, rewards and purchases. Browsers never touch it; only the API (and later the game server) does, through the repositories in `@the-cricketer/database`.

## Technology

| Concern     | Choice                                                                                               |
| ----------- | ---------------------------------------------------------------------------------------------------- |
| Database    | PostgreSQL **17** (`postgres:17.9-alpine` in Compose). Use the same major in CI, staging, production |
| ORM         | **Drizzle ORM** + `pg` (unchanged from Module 1; no second ORM was introduced)                       |
| Migrations  | drizzle-kit generated SQL plus reviewed hand-written SQL, applied forward-only                       |
| Pool        | one `pg.Pool` per process, owned by `createDatabase()`                                               |
| Identifiers | UUIDv7 generated in the application (`gen_random_uuid()` is only a SQL-level fallback)               |
| Times       | `TIMESTAMPTZ(3)`, UTC, millisecond precision so JS `Date` round-trips losslessly                     |
| Naming      | `snake_case` in SQL, `camelCase` in TypeScript, mapped by Drizzle                                    |

PostgreSQL 17 has no native `uuidv7()` (added in 18), so ids are generated by `uuidv7()` in [ids.ts](../../packages/database/src/ids.ts): time-ordered, monotonic per process, RFC 9562 layout. Static Module 0 definitions keep their string ids (`item.bat.pro_willow_01`); the two id systems are never mixed.

## What lives where

- **Static definitions** (items, shots, deliveries, pitches, formats, training, teams, achievements, career events, contracts, sponsors, XP curves, balance) stay in `game-core`. Rows only hold their string ids. PostgreSQL cannot foreign-key into TypeScript, so repositories validate ids with `DefinitionCatalog` before writing (unknown ids throw `UnknownDefinitionError`); CHECK constraints additionally enforce the id _shape_ (`^item\.[a-z0-9_.]+$`).
- **Canonical teams** are the one static concept mirrored as rows (`teams.definition_id`), because fixtures, memberships and matches need real foreign keys. Only id, optional name override and an `active` flag are stored; strength and branding stay in config.
- **Persistent state** lives in 34 tables across ten domains (the tenth, authentication, arrived in Module 3: `auth_identities`, `auth_sessions`, `auth_tokens`; Module 6 added `player_onboarding`), see [schema.md](schema.md).

## Policies

**Enums.** Statuses are `text` columns with CHECK constraints generated from constant lists in [enums.ts](../../packages/database/src/enums.ts), not PostgreSQL `ENUM` types. Adding a value is a normal drop/add-constraint migration (no `ALTER TYPE` ordering or transaction limits) and Drizzle keeps string-union types. A compile-time check (`EnumCoverageChecks`) fails the build if a Module 0 union gains a member the list is missing. Legal status moves (`MATCH_TRANSITIONS`, `CONTRACT_TRANSITIONS`, ...) are enforced in repositories with compare-and-set updates.

**JSONB.** Only for supplemental data: event/effect snapshots, contract/sponsorship terms as agreed, reward payload snapshots, training outcome, audit metadata. Anything queried, constrained or joined is a real column.

**Money and counters** are integers (`bigint` read as JS numbers, guarded by `assertSafeInt`). Floating point is never used for currency, XP, runs or quantities. `numeric` is used only for physics-like measures (`ball_speed`) and ratings (`performance_rating`).

**Soft delete** exists only on `users` (`status='deleted'` + `deleted_at`). Economic, match, contract and audit history is never deleted in normal operation.

**Business logic is not in the database.** The triggers that exist are integrity guards (append-only ledger, `updated_at`, monotonic lifetime XP, ledger-only balance writes); there are no ORM lifecycle hooks and no formulas in schema files (enforced by a test).

## Package layout

```text
packages/database/
  migrations/           committed SQL + drizzle metadata (0000 baseline, 0001 integrity triggers)
  src/schema/           Drizzle tables per domain (no imports from game-core)
  src/repositories/     explicit domain repositories (no generic BaseRepository)
  src/connection.ts     createDatabase(): pool, transaction(), ping(), repositories()
  src/errors.ts         PersistenceError family + mapDatabaseError()
  src/pagination.ts     opaque keyset cursors
  src/definitions.ts    DefinitionCatalog over game-core
  src/player-foundation.ts  atomic "create a cricketer" persistence
  src/seed/             reference + development seeds
  src/testing/          factories + isolated test-database harness
```

Repositories return plain DTOs from [records.ts](../../packages/database/src/records.ts), never Drizzle row types, and reuse Module 0 domain types (`PlayerAttributes`, `EquipmentSlot`, ...) where they exist.

## Commands

| Command               | Purpose                                                                                 |
| --------------------- | --------------------------------------------------------------------------------------- |
| `pnpm db:generate`    | Generate SQL from schema changes (development)                                          |
| `pnpm db:migrate`     | Apply pending migrations - **the only command used for staging/production**             |
| `pnpm db:migrate:dev` | `db:generate` then `db:migrate`                                                         |
| `pnpm db:seed`        | Reference data everywhere; development players only when `APP_ENV` is development/test  |
| `pnpm db:reset`       | Development only: drop everything, re-migrate. Refuses non-local hosts and non-dev envs |
| `pnpm db:studio`      | Drizzle Studio (local utility)                                                          |
| `pnpm db:check`       | PostgreSQL + Redis connectivity                                                         |
| `pnpm db:test`        | Database integration tests against isolated throwaway databases                         |
| `pnpm db:drift`       | CI: regenerate and fail if committed migrations differ from the schema                  |

Configuration variables are in [environment.md](../architecture/environment.md). Related: [decisions.md](decisions.md) for departures from the Module 2 brief, [database-security.md](../architecture/database-security.md).
