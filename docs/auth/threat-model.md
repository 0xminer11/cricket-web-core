# Threat model (Module 3)

Assets: player accounts and everything attached to them (career, wallet, inventory), credentials, sessions, recovery tokens, the integrity of the economy ledger. Actors: anonymous internet, credential-stuffing botnets, malicious web pages visiting a signed-in player, a thief with a device or cookie, other players, a curious insider with log/DB read access.

| #   | Threat                                 | Attack                                                                                                 | Mitigations (✓ = implemented and tested)                                                                                                                                                                                                                                           | Residual risk                                                                                                                   |
| --- | -------------------------------------- | ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Credential stuffing                    | Reused leaked passwords tried at scale from many IPs                                                   | ✓ per-IP `LOGIN_IP` throttle; ✓ per-email counter blocks a targeted account across IPs; ✓ Argon2id makes each guess cost ~90 ms CPU + 64 MiB; ✓ uniform error; ✓ security logs/metrics (`login_failure`, `login_blocked`)                                                          | Low-and-slow attacks under the limits. Future: breached-password check at registration, MFA, alerting                           |
| 2   | Brute-force login                      | Many guesses against one account                                                                       | ✓ per IP+email escalating temporary blocks (60 s → 1 h), no permanent lockout; ✓ length-based policy (≥10) with long passphrases allowed; ✓ block applies even to the correct password (no oracle)                                                                                 | Owner can be temporarily locked by a distributed attacker (bounded, escalating, documented trade-off)                           |
| 3   | Session theft                          | XSS/malware/network capture of the cookie                                                              | ✓ HttpOnly (script cannot read); ✓ Secure + `__Host-` in production; ✓ token never in JS, storage or URLs; ✓ only a hash in the DB (a DB leak yields no usable sessions); ✓ idle + absolute expiry; ✓ per-session revoke, `logout-all`                                             | A stolen live cookie works until revoked. Future: device list UI, anomaly detection, re-auth for risky actions                  |
| 4   | Session fixation                       | Attacker plants a known session id before login                                                        | ✓ server-generated tokens only (the client cannot choose one); ✓ rotation on login, guest upgrade and password change; ✓ the pre-login session is revoked (tested: old token → 401)                                                                                                | —                                                                                                                               |
| 5   | CSRF / login CSRF                      | Hostile page makes the browser POST with the victim's cookie                                           | ✓ SameSite=Lax; ✓ mandatory trusted Origin/Referer on every unsafe request, before any handler; ✓ strict JSON schemas; ✓ credentialed CORS only for exact trusted origins; ✓ forged logout/password-change tests                                                                   | A compromised trusted origin (XSS on the web app) is not stopped by CSRF defences — standard XSS hygiene applies                |
| 6   | Account enumeration                    | Distinguish registered vs unknown emails through login, recovery or timing                             | ✓ one login error for unknown/wrong/deleted/malformed; ✓ dummy-hash verification equalises timing; ✓ forgot-password: identical body, same throttles, async mail; ✓ block applies to unknown addresses too                                                                         | Registration intentionally says "already in use" (a signup necessity); throttled per IP                                         |
| 7   | Reset-token theft/abuse                | Intercept or guess a reset link; reuse an old one                                                      | ✓ 256-bit random, SHA-256 at rest, 1 h expiry, single-use via atomic UPDATE, purpose-bound; ✓ newer request/successful reset retire older links; ✓ token in the URL fragment (not in server logs) and scrubbed from history; ✓ reset revokes all sessions; ✓ per-IP guess throttle | A mailbox compromise yields account takeover (inherent to email recovery); MFA/re-auth is future work                           |
| 8   | Verification-token reuse               | Re-use or cross-use a verification link                                                                | ✓ single-use, purpose-scoped (a reset token cannot verify and vice versa), bound to the address, superseded by resend; ✓ idempotent re-click is harmless                                                                                                                           | —                                                                                                                               |
| 9   | Guest-account farming                  | Script creates millions of guests (storage cost, reward/ledger abuse, free-tier multiplying)           | ✓ per-IP `GUEST` throttle; ✓ no new row when a valid session exists; ✓ dead sessions swept by `auth:cleanup-sessions`; ✓ no fingerprinting                                                                                                                                         | Botnets with many IPs. Future: proof-of-work/CAPTCHA, delaying persistence until first meaningful action, pruning unused guests |
| 10  | Horizontal privilege escalation (IDOR) | Request another user's player/data by changing an id                                                   | ✓ identity only from the session; ✓ `OwnershipGuard` answers 404 for foreign/missing/malformed ids; ✓ self-service routes preferred; ✓ account id ≠ player id; ✓ `/me` ignores supplied ids                                                                                        | Every future route must use the guard; add a lint/test convention per module                                                    |
| 11  | Vertical escalation                    | Smuggle `role`/`isAdmin`/`accountType` in a request                                                    | ✓ strict schemas reject unknown fields; ✓ no role column on players; roles are a server constant; ✓ admin stays out of scope                                                                                                                                                       | Future admin system needs its own threat model                                                                                  |
| 12  | Stolen-session persistence             | Attacker keeps access after the victim "fixes" the account                                             | ✓ password reset revokes all sessions; ✓ password change revokes all others; ✓ `logout-all`; ✓ suspension is checked per request; ✓ absolute expiry                                                                                                                                | Guest sessions cannot be recovered or revoked by their owner without an account (no identity to prove)                          |
| 13  | Duplicate account / reward interaction | Same person gets multiple identities to multiply starter rewards; race two registrations; merge guests | ✓ one account per normalised email (unique index, race-tested); ✓ guest upgrade keeps the id so no reward duplication or ledger copy; ✓ no automatic merging, ever; ✓ Module 2 idempotency keys protect economy grants per player                                                  | Multiple guests per person are possible by design; reward policy for guests belongs to the economy modules (Module 0/2 rules)   |
| 14  | Pre-hijacking                          | Attacker registers a victim's address first (unverified), waits for the victim                         | ✓ victim can recover via mailbox: a reset proves ownership, revokes the attacker's sessions and marks the address verified; ✓ social linking never auto-merges on unverified email ([future-oauth](future-oauth.md))                                                               | Attacker may play on the account until the victim resets; gate sensitive features on `emailVerified` later                      |
| 15  | Insider / backup exposure              | DB or log read access                                                                                  | ✓ only hashes of passwords/tokens; ✓ no secrets in logs or audit; ✓ hashed identifiers in logs; ✓ no IPs stored                                                                                                                                                                    | Emails are personal data: apply retention and access policy (deletion workflow is future work)                                  |
| 16  | Denial of service on hashing           | Flood login/register to burn CPU/RAM                                                                   | ✓ per-IP throttles, 4 KiB body cap, bounded hash concurrency, bad reset tokens rejected before hashing, Module 1 global limiter                                                                                                                                                    | Distributed floods need edge protection (CDN/WAF)                                                                               |
| 17  | Dev conveniences leaking to prod       | Dev mailbox / insecure cookie / test user command in production                                        | ✓ config validation refuses insecure production settings; ✓ mailbox route not registered outside dev/test and loopback-only; ✓ `auth:create-test-user` refuses staging/production                                                                                                  | Operators must run production with `NODE_ENV=production`                                                                        |
