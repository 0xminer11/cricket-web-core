# Security and threat model (Module 7)

Authority rule: the client **names** a training; the server decides everything else.

| Threat                                                                                        | Control                                                                                                                                                                                                        | Evidence                                                                                                                |
| --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| **XP / skill injection** (`{ skillXp: 1000, timing: 99 }`)                                    | the body of `POST /training/:id` must be empty; unknown or non-empty bodies are rejected before any work; the only inputs are the path id and `Idempotency-Key`; nothing from the request reaches the database | API test: six forged bodies → 400, full state snapshot unchanged                                                        |
| **Replay attack** (resend a captured request)                                                 | the idempotency key is a unique `(player, key)` row; a replay returns the stored result and applies nothing; keys are per player                                                                               | API tests: replay, burst of 6 identical concurrent requests → 1 session, 1 debit                                        |
| **Currency double-spend**                                                                     | one guarded atomic debit with a ledger row per session; the balance row is locked; the player row is locked for the whole transaction                                                                          | two simultaneous purchases with funds for one → exactly one succeeds, balance 0, never negative (API and browser tests) |
| **Idempotency bypass** (same key for a different training, or fresh keys for the same intent) | the stored session's training id must match (`TRAINING_ALREADY_PROCESSED`); fresh keys are fresh, paid sessions by design and bounded by coins and the daily load                                              | API test                                                                                                                |
| **Concurrent request race** (lost XP, wrong fatigue)                                          | `SELECT ... FOR UPDATE` on `player_state` serialises a player's progression writes; XP, skill XP and fatigue are atomic SQL updates; skill XP is verified against the engine's assumption                      | three simultaneous sessions: XP, coins and fatigue all add up; each saw a different "before"                            |
| **Training another player**                                                                   | player resolved from the session by `requirePlayer`; no id in any path/query/body; history and hub are scoped to that player                                                                                   | API test with two players                                                                                               |
| **Manipulated training id**                                                                   | ids are matched against the static catalogue; anything else is `TRAINING_NOT_FOUND`; the id pattern is validated first                                                                                         | API tests                                                                                                               |
| **Locked drill bypass** (level, style, fatigue, coins, maxed)                                 | availability is re-evaluated server-side inside the transaction from freshly loaded state, never from what the UI showed                                                                                       | API tests for each reason                                                                                               |
| **Client fatigue modification**                                                               | fatigue is never accepted; it is changed only by the engine's delta in SQL, clamped 0-100                                                                                                                      | API tests                                                                                                               |
| **Mass assignment**                                                                           | request bodies are never spread into records; the controller reads the id and header only                                                                                                                      | code review, tests                                                                                                      |
| **Direct stat editing**                                                                       | no `PATCH /player/attributes` or any generic progression route exists; only the explicit repository methods run inside the training transaction                                                                | route list                                                                                                              |
| **Partial application / crash mid-way**                                                       | single transaction; a real trigger-induced failure at the last statement leaves no debit, XP, skill XP, fatigue or session                                                                                     | rollback test                                                                                                           |
| **Information leak**                                                                          | stable codes, generic 500, details only in server logs with request id/player id/training id; no stack, SQL or other players' data in responses                                                                | tests assert no SQL text in the 500 body                                                                                |
| **Telemetry abuse**                                                                           | strict schema (two events, optional id pattern), rate limited                                                                                                                                                  | route config                                                                                                            |
| **Flooding**                                                                                  | per-route rate limits (reads 120/min, start 60/min; strict in staging/production); the soft daily capacity bounds the value of spam                                                                            | route config                                                                                                            |
| **CSRF**                                                                                      | Module 3 origin guard on unsafe methods                                                                                                                                                                        | route hook                                                                                                              |
| **History tampering**                                                                         | sessions are written once as completed; there is no edit/delete route; stored results are re-validated with zod before use                                                                                     | tests                                                                                                                   |

## Notes

- Free sessions (rest) carry no ledger row but still write a session, so they are idempotent and auditable.
- Future interactive training must not trust a browser-supplied score; see [future-minigames.md](future-minigames.md).
- A session id appears in the ledger `reference_id`, tying wallet and training audit trails together.
